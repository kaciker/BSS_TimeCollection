# Issue #2 implementation

Three levels are stored in `workshops`, `subworkshops`, and `project_lines`. IDs are stable; codes are unique at their respective parent scope. A terminal stores only `project_line_id`, with the parent path derived through foreign keys. New events copy the six code and description values into nullable snapshot columns. Existing events and unassigned legacy terminals remain readable. New terminal creation requires a valid active Project / Line; existing unassigned terminals remain editable until administrators assign a path.

Admin → Structure provides table rows, search, Workshop/Subworkshop/status filters, and create/edit/activate/deactivate actions. Terminal editing uses cascading selectors. Active records with active descendants, or a leaf assigned to an active terminal, cannot be deactivated until dependencies are changed. Moving a branch with leaves or a leaf assigned to a terminal is blocked, preserving historical path meaning.

`terminal.oracle_attributes` and `time_events.oracle_attributes` remain unchanged for unrelated integration fields, including legacy Oracle context. `work_cell` remains a separate terminal exit-policy value and is excluded from outgoing events. The new normalized structure is deliberately absent from `timeEventAttributes`; Oracle/Fizz must confirm the final mapping and attribute names before adapter translation is implemented.

Migration `0009_operational_structure` adds only tables, one nullable terminal FK and six nullable event columns; it does not backfill guessed values or rewrite histories. The deployment uses `docker-compose.issue2.yml` as a Compose override for pinned local images. Build procedure, when registry access is available: build backend and frontend images, then `docker compose -f docker-compose.yml -f docker-compose.issue2.yml up -d --no-build --no-deps api worker web`. Preserve the PostgreSQL volume and do not enable Oracle transmission.
